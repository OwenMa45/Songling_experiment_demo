# 真机微调前的归一化与坐标核对

当前为遥操示范的监督模仿学习（π0.5 LoRA），不是在线 RL。目标仍是同一场景 2+2 技能展示。norm 和坐标契约是模型输入输出的一部分，不能在训练、服务、机械臂客户端各自猜测。

## 固定的数据含义

| 项目 | 本项目约定 |
| --- | --- |
| 顺序 | q1、q2、q3、q4、q5、q6、gripper_width |
| 六关节状态 | 从臂 SDK 反馈角度，rad，保留 SDK 零位和正负号 |
| 六关节原始动作 | CAN 记录的绝对位置目标，rad |
| 夹爪 | SDK 有符号坐标，m；字段虽叫 width，不能假定是非负几何间距 |
| 模型动作 | 前六维为相对当前观测的目标增量，夹爪维仍为绝对目标 |
| norm | π0.5 的 q01/q99 分位数缩放；状态、动作各自计算 |
| 图像 | front→base_0_rgb，wrist→right_wrist_0_rgb；left_wrist_0_rgb 屏蔽 |
| 图像格式 | RGB；uint8 0–255 或浮点 0–1；保比例补边至 224×224 |
| 频率/预测长度 | 当前 30 Hz、16 个目标，时间戳覆盖 t 至 t+15/30 秒 |
| 策略服务输出 | 已恢复为绝对位置目标，前六维 rad、最后一维 m |

这里没有 XYZ/四元数、世界坐标到基座坐标变换，也不需要套用 ALOHA 的关节符号和夹爪 0–1 规则。相机位置、裁剪方向、关节机械零点、夹爪零点仍应与采集时一致。摄像头序号变化时按实际画面/设备确认 front 与 wrist，不能只沿用 /dev/video 编号。

## norm 实际做什么

以当前观测 s_t 和动作块 a_t…a_(t+15) 为例：

```text
关节：u[t+k,j] = a[t+k,j] - s[t,j]   j=0..5
夹爪：u[t+k,6] = a[t+k,6]

z = 2 * (x - q01) / (q99 - q01 + 1e-6) - 1
x = (z + 1) / 2 * (q99 - q01 + 1e-6) + q01
```

整个动作块都减同一个 s_t，不是每个目标减其前一个目标，也不是角速度。例如状态 q1=0.20 rad，后续目标为 0.23、0.25，则模型目标为 0.03、0.05；恢复后为 0.23、0.25。夹爪目标 -0.0026 m 保留为 -0.0026，而不减当前夹爪反馈。

先做上述增量变换，再从训练集计算 state/actions 两套统计；随后归一化，最后填零到模型的 32 维。模型内有32维不表示双臂；统计只应有7维。mean/std 会随官方统计一起保存，但这条 π0.5 路径实际使用 q01/q99。

策略服务使用训练检查点附带的 norm 做反变换，并加回这次请求的状态一次。真机客户端收到的是绝对目标：**不要再次反归一化、再次加状态、再次累计增量或再乘控制周期**。不要把值直接当作 SDK 的毫度/微米整数；SDK API 接收何种单位必须逐方法核对。直接发 CAN 时才按已核对协议转换，避免二次换算。

分位数外的少量数据得到超出 [-1,1] 的值是正常现象；本项目不自行裁剪 action 尾部。q01≈q99 的轴会单独列出，需结合数值范围判断是否为固定姿态或异常记录。规范化不是关节限位，更不能代替执行端速度、位置、失联和急停处理。

## 本次代码检查与加固

1. 核查固定 openpi 提交的 compute_norm_stats、DeltaActions、Normalize/Unnormalize、AbsoluteActions 和策略服务：归一化在增量变换之后，服务从检查点 assets 读取统计，反变换顺序正确。
2. 单臂坐标/图像约定写入 coordinate_contract，随服务元信息、norm 审查记录及训练 piper_run.json 保存。
3. norms 使用 batch=1 计算全量训练帧，避免官方脚本按 batch 取整漏尾帧，也避免改变训练卡数/优化 batch 改变统计覆盖范围。训练 batch 仍由配置决定。
4. norms 完成后生成 piper_norm_audit.json，绑定 receipt、训练集 parquet 与元信息内容摘要、动作块长度、控制频率、坐标契约及 norm 摘要。train 和 norm-check 会重新检查。新增数据、标签变化、norm 被替换等均会报错，不静默沿用。
5. norm-check 用真实 LeRobot 动作块和官方变换做往返测试，最多均匀抽64个块：验证六关节只减一次当前状态、夹爪不减、归一化/32维填充/反归一化/绝对化恢复误差不超过 2e-6 rad或m。此测试验证软件，不代表模型预测准确。
6. serve 对检查点内的数值统计与训练审查记录做一致性检查，不会拿新统计搭配旧权重。缺审查记录的旧检查点不会自动放行；保留原始配置与统计，另行核验，不能编辑审查记录来冒充验证。
7. 拒绝浮点 0–255 图像、NaN、非预期整数类型。以前的静默 clip 可能掩盖实时相机编码错误；OpenCV 输入还需在客户端明确 BGR→RGB，本项目无法仅凭数组识别通道语义。
8. 检查 LeRobot 中 state/actions 的七维顺序、float32 和 fps，及原始 action_order/task_id 一致性。

摘要覆盖数字监督与元数据，不声称逐次重哈希所有导出图片。图片完整性由采集审查与转换验证负责，转换后保持只读。外部验证记录属于操作者提供的证据，本地软件没有重新执行硬件身份测试。

## 服务器处理步骤

使用**数据转换时同一配置、receipt 和 HF_LEROBOT_HOME**。如果之前通过 PIPER_DATASET_RECEIPT / PIPER_OUTPUT 覆盖过路径，继续沿用；不要为了通过检查修改 receipt。无需删除或重新转换已正确导出的数据。

```bash
# 在 songling 环境、项目根目录，沿用转换时的 PIPER_CONFIG 等变量。
bash scripts/run.sh --gpu-list 4 norms
bash scripts/run.sh --gpu-list 4 norm-check
```

norms 本次会重新生成统计并附上审查记录。norm-check 输出绑定信息、逐维分位数、近常量轴、抽样归一化尾部比例和往返误差。若当前工作在另一个节点或使用不同 GPU，保持该节点原有GPU选择，不必为了本命令迁移节点。也可以在已设置 CUDA_VISIBLE_DEVICES 的 songling 环境执行 `python -m piper_titration --config "$PIPER_CONFIG" norm-check`。

通过后再执行已有单步训练命令；train 会自动重复审查验证。请先提供 norm-check 输出，再决定是否需要处理异常轴。多技能合并为新数据集时重新计算整个训练集的norm，不逐回合独立归一化，也不把新的norm直接换进旧技能检查点。

## 真机仍需确认的事项与重训边界

- 现场记录同一姿态的 SDK 六关节与夹爪状态，对应关节顺序、单位、零点和符号；确认负夹爪目标在实际控制接口中的语义和可执行范围。不要因字段名字width擅自改协议坐标。
- 在不发送机械臂指令的模式下，将一帧原始观测送入服务，检查相机图像、状态单位、输出绝对目标及动作块频率；后续在已验证的控制接口上做受限动作测试。
- 控制端每次推理仅执行约定数量的动作，余下旧块被新块替换，避免断连或排队后执行过时指令。30Hz表示目标时间间隔，模型推理不必也不一定达到30次/秒。
- SDK单位、符号、BGR/RGB或反变换次数等**部署适配错误**，如果训练数据和模型约定正确，通常可以在接口修复，不自动要求重训。
- 如果训练数据本身单位混杂、关节错序、标签错误或动作时间错配，才需要修复数据、重算norm并重新训练。只修norm文件不能修复已经用错误坐标训练的模型。

软件检查可以提前阻断已知不一致，无法保证真机成功率或永远不需要重训。
